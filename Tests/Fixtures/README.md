# 縮小枠の入力を受信側で確認する

`InputProbe.swift` は自分の2ウィンドウだけで入力イベントと状態を記録するAppKitアプリです。イベントの生成、グローバル監視、他アプリの読み取りは行いません。`scripts/validate.sh` がビルド用フォルダの `input-probe/QuadDeskInputProbe` へコンパイルします。

独立した2つの `.app` に同じ実行ファイルを入れ、Info.plistで次を指定すると、4ウィンドウを検証できます。

- `CFBundleIdentifier`: インスタンスごとに異なるID
- `ProbeInstance`: `One` / `Two` などの表示名
- `ProbeLogPath`: 事前に空ファイルを作った書き込み先の絶対パス。追加の書類アクセス権限を避けるためOSの一時フォルダを使用

通常起動時は文字欄ではなく非テキストのビューがfirst responderになります。メニューの「Reset test focus」で選択とスクロールを先頭へ戻し、両ウィンドウの入力先を非テキストに戻せます。

1. QuadDeskで4つのウィンドウを選択し、開始する。各ウィンドウの元の位置・サイズを記録する。
2. QuadDeskの縮小枠内の文字欄をクリックする。**この時点で元アプリへの直接クリック・キー操作・アクティブ化を行わない。**
3. ログを読み、対象の`windowNumber`について`appActive`、`windowKey`、`textResponder`がすべてtrueになったことを確認する。別のウィンドウの状態と取り違えない。
4. その後に文字を入力し、`afterKeyDown`の文字数増加と縮小映像の変化を照合する。画面操作ツールはキー操作前に元アプリをアクティブ化する場合があるため、手順3を省略しない。この試験だけでは実キーボード入力の合格にはしない。
5. 縮小枠でスクロールし、受信イベントと`scrollOriginY`の変化を確認する。スクロールアニメーションのため、`afterScroll`直後は古い位置のことがある。後続のheartbeatも確認する。
6. 別アプリと同じアプリの別ウィンドウを含む全4枠で繰り返す。ハートビート表示が各枠で更新され、入力後も4面が維持されることを映像で確認する。
7. 中央メニューから通常停止し、全ウィンドウが元の位置・サイズに戻り、配置復元ログが`remainingRestore=0`になることを確認する。

ログには入力文字列を保存しません。文字数、イベント種類、座標、入力先状態、テストウィンドウ名、PID、時刻を記録します。スクリーンショットや映像の保存はこのfixtureには実装していません。

## ネイティブ版のChrome表示倍率（0.7.9）

上の入力転送の手順は旧方式用です。現在の倍率確認には `BrowserScaleProbe.html` をChromeの専用ウィンドウで開きます。実機確認に使ったページと同じ内容で、文字は固定24px、表示領域はリサイズ時に更新されます。外部通信はありません。

1. 通常表示で文字サイズを確認してから、Chromeと他の3ウィンドウをQuadDeskの作業モードへ選択します。
2. 4配置の完了後、Chromeの緑ボタンでフルスクリーンにします。通常の表示倍率へ復帰し、Chromeが通常の1画面へ配置され、文字が手順1と同じ大きさになることを確認します。
3. QuadDeskのDockまたはメニューから4画面へ戻し、全4枠の配置を確認します。開始前の配置記録が変わらないことも確認します。
4. 緑ボタンの通常最大化の操作でも、通常倍率の1画面になることを確認します。
5. QuadDeskを通常終了し、元配置と表示倍率への復元・復元記録の削除を確認します。試験用ウィンドウだけを閉じます。
